# 02 · 部署实战

本文按「认证 → 应用层 → 网络层 → 时间层 → 系统优化」的顺序，给出每一步的完整命令与验证方法。

> 约定：
> - 路由器 LAN 地址 `192.168.1.1`，LAN 网段 `192.168.1.0/24`
> - WAN 口名为 `wan`，LAN 桥为 `br-lan`
> - 所有 `scripts/*.py` 均通过环境变量读取连接信息（见 `scripts/common/ssh_helper.py`）

---

## 第 0 步：刷 OpenWrt 并装中文界面

K2P 对应的 target 是 `ramips/mt7621`。刷入官方固件后，先解决中文界面（离线安装）：

```sh
uci set luci.main.lang='zh_cn'
uci commit luci
/etc/init.d/uhttpd restart
```

## 第 1 步：认证 —— ESurfingClient

### 1.1 找到认证凭据

如果你电脑上装过天翼校园客户端，账号和认证环境就藏在它的配置里：

- 账号：`%APPDATA%\ChinatelecomJSPortal\Config\config.xml`
- 密码：客户端不明文存密码，需要在内存里找（本文不展开，请用你自己的合法方式获取）
- 学校 ID / Portal 域名 / Portal IP：同样在 `config.xml` 里

需要记录的认证环境信息：

| 字段 | 说明 | 示例（已脱敏） |
|---|---|---|
| 账号 | 校园网账号 | `<YOUR_ACCOUNT>` |
| 密码 | 校园网密码 | `<YOUR_PASSWORD>` |
| 学校 ID | 学校在电信侧的编号 | `<SCHOOL_ID>` |
| Portal 域名 | 认证门户域名 | `<PORTAL_DOMAIN>` |
| 区域码 | 地区编号 | `<AREA_CODE>` |
| Portal 地址 | 认证服务器 IP:端口 | `<PORTAL_IP:PORT>` |
| 通道 | 客户端类型（Android=3，Windows=1） | `1`（Windows） |

> **通道建议选 1（Windows）**：如果你原本就是用电脑客户端认证的，选 Windows 通道能匹配原客户端的 User-Agent（如 `CCTP/WinSVR5/...`），避免因通道不符导致的套餐/限速问题。

### 1.2 安装并配置

```sh
# 离线安装主程序 + LuCI 插件（依赖包一并装上）
apk add --allow-untrusted ./esurfingclient-*.apk
apk add --allow-untrusted ./luci-app-esurfingclient-*.apk

# 写入配置
cat > /etc/config/esurfingclient <<'EOF'
config service 'service'
    option enabled '1'
    option account '<YOUR_ACCOUNT>'
    option password '<YOUR_PASSWORD>'
    option channel '1'
    ...
EOF

/etc/init.d/esurfingclient enable
/etc/init.d/esurfingclient start
```

### 1.3 验证

```sh
logread | grep -i esurfing | tail -20      # 看到「认证成功」「发送心跳包」即可
ip -4 addr show wan                         # WAN 应拿到运营商分配的内网地址
ip route | grep default                     # 应有默认路由
ping -c 3 223.5.5.5                         # 外网可达
```

**认证成功后的两个机制**（理解它们有助于排错）：

- **心跳保活**：认证成功后，Portal 会下发一个心跳间隔（天翼是 **250 秒**），客户端定期发心跳维持会话。这个间隔由服务端下发，本地改不了。
- **重试退避**：认证失败后不会死循环重试，而是按硬编码表 **`{1, 5, 10, 20, 30}` 分钟**（即 60s → 1800s）递增，最多 5 次。所以**一次开机认证失败，最坏要等 30 分钟才能恢复**——这正是为什么第 4 步要给认证加启动延迟，也是为什么后面要用守护脚本把重试压到约 1 分钟（见 5.8）。

## 第 2 步：应用层 —— UA2F

### 2.1 为什么不用 UA3F

K2P 的 overlay 分区只有 **7.6MB**，UA3F 主程序需要 **17.6MB**，根本装不下。UA2F 主程序仅 **758KB**，核心的 UA 改写功能完全一致。

```sh
df -h /overlay          # 先看剩余空间，再决定装什么
```

### 2.2 安装

```sh
apk add --allow-untrusted ./ua2f-*.apk ./libnetfilter_queue-*.apk ...   # 依赖一并装
```

### 2.3 配置（NFQUEUE 模式）

```
config ua2f 'enabled'
    option enabled '1'

config ua2f 'firewall'
    option handle_fw '1'          # 处理 HTTP
    option handle_tls '0'         # 不处理 TLS（无法改写加密流量）
    option handle_intranet '1'    # 处理内网流量

config ua2f 'main'
    option mode 'NFQUEUE'
    option listen_port '10010'
    option nfqueue_workers '1'
    option proxy_workers '0'
    option custom_ua 'Mozilla'    # 越短覆盖越广，见 01-检测原理.md
    option disable_connmark '0'
    option max_http_sessions '0'
    option session_ttl '300'
```

```sh
uci commit ua2f
/etc/init.d/ua2f enable
/etc/init.d/ua2f restart
```

### 2.4 验证

```sh
nft list table inet ua2f | grep -E 'dport|queue'
```

然后**从内网任意设备**访问 <http://ua-check.stagoh.com/>，应该看到 UA 已被改成 `Mozilla`。

也可以用 `scripts/90-verify-ua-length.py` 批量验证不同长度的 UA 改写结果。

## 第 3 步：网络层 —— TTL 归一化

### 3.1 安装独立的 init 脚本

**关键设计**：用**独立的 nft 表** `ttl_normalize`，而不是往 `fw4` 的表里加规则。因为 `fw4` 或 UA2F 重启时会重建自己的表，独立表不会被误清。

```sh
cat > /etc/init.d/ttl-normalize <<'EOF'
#!/bin/sh /etc/rc.common
START=99
STOP=10
NFT_TABLE=ttl_normalize

start() {
    nft delete table inet "$NFT_TABLE" 2>/dev/null
    nft -f - <<NFT
table inet $NFT_TABLE {
    chain postrouting {
        type filter hook postrouting priority mangle + 10; policy accept;
        oifname "wan" ip ttl set 64
        oifname "wan" ip6 hoplimit set 64
    }
}
NFT
}
stop()  { nft delete table inet "$NFT_TABLE" 2>/dev/null; }
reload(){ stop; start; }
boot()  { start; }
EOF

chmod 755 /etc/init.d/ttl-normalize
/etc/init.d/ttl-normalize enable
/etc/init.d/ttl-normalize start
```

> `priority mangle + 10` 保证在 UA2F 之后再处理。

### 3.2 验证

在路由器上临时加载一个「反证表」，把 LAN 出向 TTL 改成 55，再从内网 ping 外网并抓包：

```sh
nft -f - <<'EOF'
table inet ttl_probe {
    chain postrouting {
        type filter hook postrouting priority mangle + 20; policy accept;
        oifname "br-lan" ip ttl set 55
    }
}
EOF
# 抓包应看到 TTL=64（说明 WAN 出口的 ttl_normalize 生效）
# 验证后删除：
nft delete table inet ttl_probe
```

## 第 4 步：时间层 —— NTP 重定向

### 4.1 开启路由器 NTP 服务端模式

```sh
uci set system.ntp.enable_server='1'    # 给 ntpd 加 -l，应答客户端请求
uci commit system
/etc/init.d/sysntpd restart
```

> **不要**设置 `system.ntp.interface`。用 `-I <ifname>` 绑定接口有风险，可能破坏路由器自身的外网 NTP 同步。靠 fw4 默认的 WAN input 策略防护即可。

### 4.2 强制内网 NTP 走路由器

```sh
cat > /etc/init.d/ntp-redirect <<'EOF'
#!/bin/sh /etc/rc.common
START=99
STOP=10
NFT_TABLE=ntp_redirect

start() {
    nft delete table inet "$NFT_TABLE" 2>/dev/null
    nft -f - <<NFT
table inet $NFT_TABLE {
    chain prerouting {
        type nat hook prerouting priority dstnat; policy accept;
        iifname "br-lan" ip daddr != 192.168.1.0/24 udp dport 123 counter redirect to :123
    }
}
NFT
}
stop()  { nft delete table inet "$NFT_TABLE" 2>/dev/null; }
reload(){ stop; start; }
boot()  { start; }
EOF

chmod 755 /etc/init.d/ntp-redirect
/etc/init.d/ntp-redirect enable
/etc/init.d/ntp-redirect start
```

### 4.3 验证

```sh
# 在路由器上监听 123 端口应看到监听
netstat -lnup | grep ':123 '

# 内网设备向一个不可路由的地址发 NTP 请求，若收到合法应答即证明被劫持
# 例如：ntpdate -q 203.0.113.1
```

同时用 `nft list table inet ntp_redirect` 看计数器是否在增长。

## 第 5 步：系统优化

### 5.1 认证开机延迟（重要）

`/etc/init.d/esurfingclient` 的 `boot()` 里默认 `sleep 5`，但开机 5 秒时 WAN 往往还没就绪，认证必然失败并进入 5 分钟退避。

```sh
sed -i '/^boot() {/,/^}/ s/sleep 5/sleep 30/' /etc/init.d/esurfingclient
```

验证：重启路由器，观察 `logread | grep -i esurfing`，应一次认证成功、无退避。

### 5.2 内核 socket 缓冲调优（消除 UA2F 报错）

UA2F 会报 `Conntrack catch error: No buffer space available`，原因是默认 `net.core.rmem_max` 只有 176KB（180224 字节），netlink socket 缓冲溢出。

```sh
cat >> /etc/sysctl.conf <<'EOF'
# ua2f netlink buffer tuning
net.core.rmem_max = 4194304
net.core.rmem_default = 4194304
EOF
sysctl -p /etc/sysctl.conf
/etc/init.d/ua2f restart
```

> 这个报错本身只是日志噪声（不影响数据面改写），但调大后可以彻底消除。

### 5.3 时区与 NTP 源

```sh
uci set system.@system[0].zonename='Asia/Shanghai'
uci set system.@system[0].timezone='CST-8'
uci -q delete system.ntp.server
uci add_list system.ntp.server='ntp.aliyun.com'
uci add_list system.ntp.server='ntp1.aliyun.com'
uci add_list system.ntp.server='time1.cloud.tencent.com'
uci add_list system.ntp.server='ntp.ntsc.ac.cn'
uci add_list system.ntp.server='cn.pool.ntp.org'
uci set system.ntp.enabled='1'
uci commit system
/etc/init.d/sysntpd enable
/etc/init.d/sysntpd restart
```

> 校园网下 `ntp.tencent.com` 无法解析，要用 `time1.cloud.tencent.com`。

### 5.4 5G 固定到非 DFS 信道

5GHz 信道设成 `auto` 时，ACS 可能选到 DFS 信道（如 56），开机触发 60 秒 CAC 雷达检测，导致重启后约 70 秒没有 5G。

```sh
uci set wireless.radio1.channel='149'   # CN 下 149/153/157/161/165 为非 DFS
uci commit wireless
wifi reload
```

> CN 可用非 DFS 信道：2.4G 用 1/6/11；5G 用 36/40/44/48（UNII-1）或 149~165（UNII-3）。52~64 是 DFS，100~144 不可用。

### 5.5 软件源与常用插件

OpenWrt 25.12 的 apk feed 已经配好在 `/etc/apk/repositories.d/distfeeds.list`，**不要**再手工创建 `/etc/apk/repositories`（apk 会自己拼架构后缀，导致 404）。

```sh
apk update
apk add luci-app-nlbwmon      # 流量统计
apk add luci-app-watchcat     # 断网自动重启

# watchcat 探测目标改成国内可达的地址（默认 8.8.8.8 在校园网可能被限速/拦截）
uci set watchcat.@watchcat[0].pinghosts='223.5.5.5'
uci commit watchcat
/etc/init.d/watchcat restart
```

也可直接跑 `scripts/60-install-extra-apps.sh`（装插件 + 改探测目标一步到位）。

### 5.6 DNS 与 IPv6 优化（消除「刷视频先卡几秒」）

**前提判断**：只有 **WAN 没有 IPv6 上游**时才需要这一步。若你学校提供原生 IPv6，请跳过。

```sh
# a) 关掉 LAN 侧 IPv6 RA / DHCPv6（LAN 有 IPv6 而 WAN 没有，是「卡一下」的经典元凶）
uci set dhcp.lan.ra='disabled'
uci set dhcp.lan.dhcpv6='disabled'
uci set dhcp.lan.ndp='disabled'

# b) 过滤 AAAA 记录，让客户端直接用 IPv4
uci set dhcp.@dnsmasq[0].filter_aaaa='1'

# c) 忽略 WAN 下发的（又慢又不稳的）DNS，改为分流
uci set dhcp.@dnsmasq[0].noresolv='1'
uci -q delete dhcp.@dnsmasq[0].server
uci add_list dhcp.@dnsmasq[0].server='223.5.5.5'
uci add_list dhcp.@dnsmasq[0].server='119.29.29.29'
uci add_list dhcp.@dnsmasq[0].server='/example.edu.cn/172.16.0.1'   # 校内域名 -> 校园 DNS
uci commit dhcp
/etc/init.d/dnsmasq restart
```

也可直接跑 `scripts/43-optimize-dns-ipv6.py`（校内域名 / 校园 DNS 用环境变量覆盖）。

**验证**：`nslookup -query=AAAA` 查不到记录、`nslookup -query=A` 正常、外部域名秒回、
校内域名仍能解析到内网 IP。

> 详细原理与排错见 `docs/03-踩坑与排错.md` 坑 14。

### 5.7 zram 压缩交换（防止内存盘耗尽导致重启）

K2P 只有 128MB 内存，`/var/log`、`/tmp`、nlbwmon 数据库都在 tmpfs。
tmpfs 页（shmem）**不属于任何进程、无 swap 时无法换出**，一旦吃满内存，内核会卡死并被**硬件看门狗复位** —— 表现为「莫名重启」。

```sh
apk add kmod-zram zram-swap
/etc/init.d/zram enable
/etc/init.d/zram start
```

或直接跑 `scripts/80-install-zram.sh`。

**验证**：`cat /proc/swaps` 有 `/dev/zram0`；`free -m` 显示 Swap > 0；`/etc/rc.d/` 有 zram 开机链接。

> 要调整交换分区大小，改 `uci set system.@system[0].zram_size_mb='64'`（单位 MiB）
> 后 `/etc/init.d/zram restart`。本包**没有** `/etc/config/zram` 这个文件。

> 详细复现过程见 `docs/03-踩坑与排错.md` 坑 15。

### 5.8 认证失败加速重试

ESurfingClient 的重试退避表是**硬编码**的 `{1, 5, 10, 20, 30}` 分钟，改配置改不动。
用外部守护脚本 + cron 把它压到约 1 分钟：

```sh
# 脚本 44 会写入 /usr/bin/esurfingclient-watchdog.sh 并加 cron 条目
python scripts/44-setup-esurfing-watchdog.py
```

**验证**：`cat /etc/crontabs/root` 有该条目；`ps w | grep '[c]rond'` 在跑；
有网时手动执行守护脚本应无动作。

> 详细原理见 `docs/03-踩坑与排错.md` 坑 16。

## 完整执行顺序

```
0. 刷机 + 中文界面
1. ESurfingClient 认证          → 确认能上网
2. UA2F 安装 + 配置             → 确认 UA 被改写
3. UA2F 限制 br-lan（关键）      → 确认认证不被干扰
4. TTL 归一化                   → 抓包确认 TTL=64
5. NTP 重定向                   → 确认计数器增长
6. 认证启动延迟 30s             → 重启后一次认证成功
7. rmem 调优                    → UA2F 无报错
8. 时区 + NTP 源                → 时间正确
9. DNS 反重绑定                 → 校内站点可访问
10. DNS + IPv6 优化             → 刷视频不再先卡几秒
11. 认证重试守护                → 失败后约 1 分钟恢复
12. 5G 非 DFS 信道              → 重启后快速有网
13. 软件源 + 插件（可选）        → nlbwmon / watchcat
14. zram 压缩交换               → 不再莫名重启
```

上面 0~14 是「让路由器跑起来」的主线，顺序与 `scripts/README.md` 的脚本编号一致。
**固定 IP / 端口转发**见 `docs/05-固定IP与远程访问.md`（脚本 70、71）；
**UA 改写覆盖验证**见 `docs/04-验证与运维.md`（脚本 90）。

每一步都必须**先验证再进入下一步**，否则出问题很难定位。
