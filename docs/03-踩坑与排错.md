# 03 · 踩坑与排错

这一篇记录实战中真正卡住过我的问题，以及每个问题的**现象 → 定位 → 根因 → 解决**。

---

## 坑 1：UA3F 装不上

**现象**：`apk add ua3f` 报空间不足。

**定位**：

```sh
df -h /overlay
# /dev/mtdblock7  7.6M  4.1M  3.5M  54% /overlay
apk info -a ua3f | grep 'installed size'   # 17.6 MB
```

**根因**：K2P 的 overlay 分区总共只有 7.6MB，UA3F 光主程序就 17.6MB。

**解决**：改用 UA2F（主程序 758KB），核心 UA 改写功能一致。

---

## 坑 2：装完 UA2F 后，校园网认证失败「提取门户配置失败」

**现象**：UA2F 起来后，ESurfingClient 反复报「提取门户配置失败」，认证不了。

**定位**：

```sh
logread | grep -i esurfing
# 认证流程第一步要访问 config.campus.js.chinatelecom.com 获取门户配置
# 但请求失败
nft list table inet ua2f | grep -E 'queue|iifname'
# 发现 NFQUEUE 规则没有限定入接口 —— 路由器自己的 HTTP 请求也被送进了队列
```

**根因**：UA2F 默认对所有经过转发的 TCP 流量做处理，**把路由器自身发起的认证 HTTP 请求也改写了**，导致门户配置解析失败。

**解决**：给 NFQUEUE 规则加上 `iifname "br-lan"`，只处理内网客户端流量。

```sh
# 在 /etc/init.d/ua2f 中，把
#   meta l4proto tcp ct direction original counter $nfqueue_expr
# 改成
#   meta l4proto tcp ct direction original iifname "br-lan" counter $nfqueue_expr
sed -i 's|ct direction original counter $nfqueue_expr|ct direction original iifname "br-lan" counter $nfqueue_expr|' /etc/init.d/ua2f
/etc/init.d/ua2f restart
```

**教训**：这是最隐蔽的坑。**只要路由器自己需要发 HTTP 请求（认证、DDNS、在线检查更新），UA2F 就必须限制入接口**，否则会把路由器自己「洗」坏。

## 坑 3：重启后 UA2F 补丁丢失

**现象**：手工 `nft add` 的规则，重启后没了，认证又开始失败。

**根因**：只改了运行时的 nft 表，没有写回 `/etc/init.d/ua2f` 的启动脚本。重启后 UA2F 用默认规则重建表，覆盖了手工修改。

**解决**：把补丁写进 `/etc/init.d/ua2f` 的启动脚本（见坑 2），重启后自动生效。

**教训**：**任何 nft / iptables 运行时修改，都要落到某个开机脚本里**，否则重启即失效。

---

## 坑 4：重启后网络恢复很慢（约 70 秒才通）

**现象**：重启路由器后，要等 1 分多钟才有网。

**定位**：

```sh
# 1. 先看是不是认证退避
logread | grep -i esurfing        # 认证是成功的，排除
# 2. 看无线
iw dev phy1-ap0 info | grep channel
# channel 56 (5280 MHz)  ← DFS 信道！
logread | grep -iE 'DFS|CAC'
# CAC (Channel Availability Check) 60 秒
```

**根因**：5GHz 信道设成 `auto`，ACS 自动选到了 DFS 信道 56。DFS 信道开机要做 **60 秒 CAC 雷达检测**，期间 5G AP 不可用。

**解决**：固定到非 DFS 信道 149。

```sh
uci set wireless.radio1.channel='149'
uci commit wireless
wifi reload
```

重启后 5G 在 35~45 秒就绪。

**补充**：`/var/log` 默认在 tmpfs（内存）里，**重启即清空**，所以重启前的日志事后查不到。
本项目已把日志落盘并记录启动历史（见 `08-持久日志与重启诊断.md`），无需再手工导出。

## 坑 5：UA2F 反复报 `Conntrack catch error: No buffer space available`

**现象**：日志里 UA2F 频繁报错。

**定位**：

```sh
sysctl net.core.rmem_max
# net.core.rmem_max = 180224   ← 只有 176KB
```

**根因**：内核 netlink socket 接收缓冲太小，conntrack 事件通知溢出。

**验证是否影响业务**：跑 160 次并发 HTTP 请求，在报错窗口内统计改写成功率，结果为 **160/160 全部改写成功** —— 说明该报错只影响「事件通知」，不影响数据面的包改写。

**解决**（消除噪声）：

```sh
cat >> /etc/sysctl.conf <<'EOF'
# ua2f netlink buffer tuning
net.core.rmem_max = 4194304
net.core.rmem_default = 4194304
EOF
sysctl -p /etc/sysctl.conf
/etc/init.d/ua2f restart
```

调整后连续观察 45 分钟，错误计数保持为 **0**。

## 坑 6：升级软件包时 SSH 断连，升级失败

**现象**：`apk upgrade` 升到 `netifd` / `wpad` 时，网络服务重启，SSH 掉线，升级中断。

**解决**：把升级脚本上传到路由器，用 `setsid` 脱离终端后台跑，与 SSH 会话解耦。

```sh
setsid sh /tmp/do_upgrade.sh > /tmp/upgrade.log 2>&1 &
```

之后轮询 `/tmp/upgrade.log` 看进度，升级完再重启。

## 坑 7：`apk upgrade` 不升级中文语言包

**现象**：`apk list -u` 明明显示有更新，`apk upgrade` 却跳过了几个 `luci-i18n-*-zh-cn`。

**根因**：这些包在 `/etc/apk/world` 里被**版本哈希锁定**（形如 `pkg><hash>`），`apk upgrade` 默认不动锁定包。

**解决**：用 `apk add --upgrade` 强制升级指定包。

```sh
apk add --upgrade luci-i18n-base-zh-cn
apk add --upgrade luci-i18n-firewall-zh-cn
```

## 坑 8：LuCI 访问返回 403，以为坏了

**现象**：浏览器访问 `http://192.168.1.1/cgi-bin/luci/` 返回 403。

**定位**：抓响应体发现 —— 403 的 body 其实**就是中文登录页**（`OpenWrt | 概览` + 用户名密码表单 + 登录按钮）。

**根因**：LuCI 对**未登录**的受保护页面返回 HTTP 403，同时渲染登录表单，让浏览器显示登录界面。这是设计行为，不是故障。

**解决**：无需处理。登录后即正常。

---

## 坑 9：`uci show` 报 `Parse error (invalid command) at line 1`

**现象**：`uci show` 输出一行 `Parse error (invalid command) at line 1, byte 0`。

**定位**：

```sh
uci show >/dev/null 2>&1; echo $?   # 退出码 0
# /etc/config/ 下有非 uci 格式的文件（如某些客户端的 JSON 日志）
ls /etc/config/
```

**根因**：`/etc/config/` 目录里混进了非 uci 格式的文件（本例是认证客户端写的 JSON 文件），uci 遍历时解析失败报警，但**会跳过该文件继续处理其他配置**。

**验证影响**：`uci show` / `uci commit` 退出码均为 0，LuCI 和系统功能正常。

**解决**：无需处理。若强迫症可把非 uci 文件挪出 `/etc/config/`。

## 坑 10：`apk` 源报 404 / "N unavailable"

**现象**：`apk update` 时大量 404 警告。

**根因**：手工创建了 `/etc/apk/repositories` 并写入了裸 URL。apk 会自己在 URL 后面拼架构（`<url>/<arch>/APKINDEX.tar.gz`），导致找不到。

**解决**：OpenWrt 25.12 的 feed 已经配在 `/etc/apk/repositories.d/distfeeds.list`，**不要**再手工创建 `/etc/apk/repositories`。那些警告本身也无害。

## 坑 11：K2P 无线功率改不动

**现象**：想提高 WiFi 信号，改国家码 / 设 txpower 都无效。

**定位**：

```sh
iw phy phy0 info | grep -A2 '2412.0 MHz'
# * 2412.0 MHz [1] (8.0 dBm)     ← 驱动标定就是 8 dBm
iw reg get
# country CN: (2400 - 2483 @ 40), (N/A, 20)   ← 法规允许 20 dBm
# 尝试手动设置
iw dev phy0-ap0 set txpower fixed 1100   # 想设 11 dBm
iw dev phy0-ap0 info | grep txpower
# txpower 8.00 dBm   ← 被驱动拒绝，仍是 8
```

**根因**：MT7615 驱动 / EEPROM 把发射功率**硬编码**在 8 dBm，与法规无关。国家码、`txpower` 配置都改不动。

**结论**：想在配置层提升功率是**不可能的**，只能重编译 mt76 驱动（改 `mt7615_init_txpower()`）或改 EEPROM，代价高且可能导致信号质量（EVM）劣化。**不建议折腾**，换更好的路由器或用 AP/Mesh 扩展更实际。

## 坑 12：`luci-app-ttyd` 装不上

**现象**：想装 Web 终端，依赖链爆炸。

**定位**：

```sh
apk info -a luci-app-ttyd | grep depends
# ttyd 硬依赖 libwebsockets-full → libopenssl3（4470 KiB）
# 合计约 5.5MB，而 overlay 只剩 5.9MB，勉强但风险高
```

**根因**：`libwebsockets-mbedtls` 虽然提供虚拟包 `libwebsockets`，但无法满足 ttyd 对**具体包名** `libwebsockets-full` 的依赖。

**解决**：放弃 ttyd，直接用 SSH。

## 坑 13：校内站点（教务系统）打不开，换热点就正常

**现象**：外网一切正常，但学校教务系统打不开；把电脑换成手机热点，立刻就能访问。
同一台电脑、同一个域名，只有走这台路由器时不行。

**定位**：

```sh
# 在路由器上用本地 dnsmasq 解析这个域名
nslookup jwxt.example.edu.cn 127.0.0.1
# 应答里这个「公网域名」被解析到了一个内网地址（172.16.x.x）

# 看 dnsmasq 的启动参数
ps w | grep '[d]nsmasq' | grep stop-dns-rebind
# 有 --stop-dns-rebind
```

**根因**：dnsmasq 默认开启**反重绑定保护**（`rebind_protection=1`），会丢弃
「公网域名解析到私有 IP」的应答 —— 这是防 DNS rebinding 攻击的**正常机制**。
但很多学校的校内系统就是这么解析的（校园网内部用私有地址互访），于是被误伤。

之所以换热点就正常：手机热点下 DNS 用的是运营商递归，没有这层保护。

**解决**：关闭反重绑定保护。

```sh
uci set dhcp.@dnsmasq[0].rebind_protection='0'
uci commit dhcp
/etc/init.d/dnsmasq restart
```

**验证**：

```sh
ps w | grep '[d]nsmasq' | grep -q stop-dns-rebind && echo '仍有保护' || echo '已关闭'
nslookup jwxt.example.edu.cn 127.0.0.1     # 现在应能拿到应答
nslookup www.baidu.com 127.0.0.1           # 顺带确认 DNS 整体没坏
```

**权衡**：全局关闭后，内网 DNS 不再拦截「公网域名 → 私有 IP」的应答，理论上
增加了 DNS rebinding 风险。如果只是要访问校内站点，更稳妥的是**只放行特定域名**：

```sh
uci add_list dhcp.@dnsmasq[0].rebind_domain='example.edu.cn'
uci commit dhcp
/etc/init.d/dnsmasq restart
```

把 `example.edu.cn` 换成你学校的域名后缀即可（多个域名就 `add_list` 多次）。

**教训**：排查「某个域名打不开」时，**先用路由器本机 `nslookup` 解析一次**，
能直接区分「解析层被拦」还是「转发/链路问题」。这次现象看起来像网络不通，
实际是路由器在 DNS 层就把它拒了。

## 坑 14：刷视频 / 开网页老是「先卡几秒」才加载

**现象**：外网是通的，ping 也正常，但刷视频、开网页经常先转圈几秒，然后突然开始加载；
换到手机热点上同样的网站却很快。

**定位**：

```sh
# 1. 看 LAN 是否在广播 IPv6，而 WAN 有没有 IPv6 上游
ip -6 addr show dev br-lan | grep 'inet6.*scope global'   # LAN 有 IPv6
ip -6 addr show dev wan    | grep -c 'inet6.*scope global' # WAN 没有 -> 0

# 2. 看 DNS 是否返回了 AAAA 记录
nslookup -query=AAAA www.bilibili.com 127.0.0.1
# 返回了 IPv6 地址

# 3. 测外部域名的解析耗时
time nslookup www.qq.com 127.0.0.1
# 好几秒才回来 —— WAN 下发的校园 DNS 又慢又不稳
```

**根因（两条叠加）**：

1. **IPv6 假阳性**：路由器 LAN 侧开了 RA / DHCPv6，内网设备拿到了 IPv6 地址；
   DNS 又返回了 AAAA 记录。于是客户端**优先尝试 IPv6 连接**，而 WAN 侧根本没有 IPv6 上游，
   每次都要等 IPv6 超时后才回退 IPv4 —— 每个新连接都白白慢一拍。
2. **DNS 慢**：WAN 的 DHCP 下发了一个又慢又不稳的校园 DNS，外部域名解析要等好几秒。

**解决**：三件事一起做（`scripts/43-optimize-dns-ipv6.py`）。

```sh
# a) 关掉 LAN 侧 IPv6 RA / DHCPv6（WAN 无 IPv6 上游时不该向内网广播）
uci set dhcp.lan.ra='disabled'
uci set dhcp.lan.dhcpv6='disabled'
uci set dhcp.lan.ndp='disabled'

# b) 过滤 AAAA 记录，让客户端直接用 IPv4
uci set dhcp.@dnsmasq[0].filter_aaaa='1'

# c) 忽略 WAN 下发的 DNS，改为分流：
#    默认外部域名走公共 DNS（换成本线路运营商 DNS 通常更快，见下文实测）
#    校内域名定向到校园 DNS
uci set dhcp.@dnsmasq[0].noresolv='1'
uci -q delete dhcp.@dnsmasq[0].server
uci add_list dhcp.@dnsmasq[0].server='223.5.5.5'
uci add_list dhcp.@dnsmasq[0].server='119.29.29.29'
uci add_list dhcp.@dnsmasq[0].server='/example.edu.cn/172.16.0.1'   # 换成你学校的
uci commit dhcp
/etc/init.d/dnsmasq restart
```

**验证**：

```sh
nslookup -query=AAAA www.bilibili.com 127.0.0.1   # 应查不到 AAAA
nslookup -query=A    www.bilibili.com 127.0.0.1   # A 记录正常
nslookup www.qq.com 127.0.0.1                     # 应秒回（走公共 DNS）
nslookup jwxt.example.edu.cn 127.0.0.1            # 校内域名仍能解析到内网 IP
```

**DNS 上游怎么选（实测）**：不要盲抄公共 DNS —— **就近的运营商 DNS 通常更快**。
在校园电信线路上实测（6 个域名 × 4 次取平均，从路由器发起）：

| DNS 上游 | 平均响应 | 说明 |
|---|---|---|
| 运营商 DNS（广东电信 `202.96.128.166` / `202.96.128.86`） | **10.8 ms** | 抖音 CDN 返回省内电信节点 |
| `223.5.5.5`（阿里公共） | 15.0 ms | 慢约 40% |
| `119.29.29.29`（腾讯公共） | 17.5 ms | 慢约 60% |

**结论：按线路就近选** —— 电信线路用电信 DNS、联通线路用联通 DNS、移动线路用移动 DNS，
再叠加校内域名定向分流；公共 DNS 作为备选。

**注意**：关掉 LAN IPv6 后，内网设备要**重连 WiFi / 重续租约**才会丢掉旧的 IPv6 地址，
否则设备上残留的 IPv6 地址仍会先被尝试。

**教训**：**LAN 有 IPv6、WAN 没有 IPv6 上游**，是「能上网但经常卡一下」的经典元凶。
要么两端都开，要么两端都关，**千万不要半开**。

## 坑 15：路由器频繁「莫名其妙重启」

**现象**：路由器会毫无规律地自己重启（无超频、无掉电），重启后一切正常，过一段时间又来一次。
`/var/log` 在 tmpfs，重启即清空，事后查不到任何线索。

**定位**：这类「查不到日志的重启」通常是**内核卡死被硬件看门狗复位**，而不是正常重启。
用「内存压力 + 观察 uptime 是否单调」的方式复现：

```sh
# 1. 记录当前 uptime 与内存
cut -d. -f1 /proc/uptime; free -m

# 2. 制造内存盘压力（往 tmpfs 里灌数据）
dd if=/dev/zero of=/tmp/fill bs=1M count=40

# 3. 同时跑几路并发下载，持续观察 uptime 是否被清零
while :; do cut -d. -f1 /proc/uptime; free -m | head -2; sleep 5; done
```

**根因**：K2P 只有 128MB 内存，而 `/var/log`、`/tmp`、nlbwmon 数据库都放在 **tmpfs（内存盘）**。
tmpfs 的页属于 **shmem**，**既不属于任何可被 OOM killer 杀掉的进程，在没有 swap 时也无法换出**。
一旦内存盘把内存吃满，内核会陷入回收活锁，最终被**硬件看门狗复位** —— 表现为「莫名其妙重启」。

**解决**：加一个 **zram 压缩交换**，给内存压力一个泄洪口（`scripts/80-install-zram.sh`）。

```sh
apk add kmod-zram zram-swap
/etc/init.d/zram enable
/etc/init.d/zram start
```

**验证**：

```sh
cat /proc/swaps                 # 应看到 /dev/zram0
free -m                         # Swap 总量应大于 0
ls -l /etc/rc.d/ | grep zram    # 应有开机自启链接
```

复现压力后，`uptime` 应**单调递增**（不再被清零），zram 的 used 会随压力上升。

**教训**：tmpfs 页（shmem）在没有 swap 时**不可回收**，这是内存盘型路由器「卡死复位」的根因。
**zram 压缩交换不是可有可无的优化，而是这类小内存路由器的保命配置**。

## 坑 16：认证失败后要干等好几分钟才恢复

**现象**：偶发认证失败（或校园网侧把会话踢掉）后，要等好几分钟才恢复上网。

**定位**：

```sh
logread | grep -i esurfing | tail -20
# 能看到失败后隔了很久才进行下一次重试
```

**根因**：ESurfingClient 的重试退避表是**硬编码**的 `{1, 5, 10, 20, 30}` 分钟，最多 5 次，
**改配置改不动**。所以一次失败，最坏可能要 5 分钟后才轮到下一次重试。

**解决**：部署一个外部守护脚本，用 cron **每分钟**检查一次（`scripts/44-setup-esurfing-watchdog.py`）。

```sh
# 逻辑：认证进程在、且外网可达 -> 什么都不做
#       认证进程在、但外网不通 -> 重启认证服务（顺带触发补偿登出）
#       带 50 秒限流，避免反复重启形成风暴
cat > /usr/bin/esurfingclient-watchdog.sh <<'EOF'
...（见脚本 44）...
EOF
chmod +x /usr/bin/esurfingclient-watchdog.sh
echo '* * * * * /usr/bin/esurfingclient-watchdog.sh' >> /etc/crontabs/root
/etc/init.d/cron enable
/etc/init.d/cron restart
```

**验证**：

```sh
cat /etc/crontabs/root                       # 有这一行
ps w | grep '[c]rond'                        # cron 在跑
/usr/bin/esurfingclient-watchdog.sh; echo $? # 当前有网时应无动作
cat /tmp/esurfing-watchdog.log               # 只有真触发重启时才有记录
```

**教训**：把最坏恢复时间从「分钟级」压到「约 1 分钟」。
重启认证服务会顺带触发一次补偿登出，**有助于清掉服务端卡住的在线会话**。

## 坑 17：满速下载时路由器 CPU 飙升、页面卡顿

**现象**：大流量下载（如 Steam）时路由器 CPU 明显升高、整机响应变慢，下载也跑不满线路。

**定位**：

```sh
nft list table inet ua2f | grep -E 'header-only|to 10010'
# 隔 10 秒再看一次：queue 计数器约 3100 包/秒在涨——几乎全是下载流的纯 ACK
```

**根因**：NFQUEUE 规则匹配 br-lan 全部原始方向 TCP。下载流 99% 的包是无负载的纯 ACK
（不可能含 User-Agent），但每包都要走一遍「内核 → 用户态 → 判决」的往返，880MHz 的 CPU 直接被吃满。

**解决**：在入队规则前插入两条按长度旁路规则（`scripts/12-patch-ua2f-ack-bypass.py`）：

```sh
ip length 1-80     counter return   # v4：纯 ACK 总长最多 80B（TCP 选项拉满时），阈值含边界覆盖
ip6 length 1-104   counter return   # v6：ip6 length 是负载长度，纯 ACK 负载最多 60B，阈值有余量
```

**验证**：队列速率降到 10~16 包/秒；`sys` 时间下降约 28%；同线路下载速率 +10%~15%；
再访问 UA 检测页确认改写仍生效。

**教训**：NFQUEUE 只适合「少量、需要深度处理」的包；大流量路径上先用 nft 把确定不用处理的包旁路掉。
完整原理与实测数据见 `docs/06-CPU与收包性能调优.md`。

## 坑 18：满速下载丢包 7%~11%，总有一个核被吃满

**现象**：修完坑 17 后 CPU 降了，但丢包率仍有 7%~11%，某个核一直 100%，速率上不到峰值。

**定位**：

```sh
cat /proc/net/softnet_stat                     # 每行一个核，第 2 列 dropped 在涨
cat /sys/class/net/wan/queues/rx-0/rps_cpus    # 4 —— 收包只给了 cpu2
```

**根因**：OpenWrt 默认 `packet_steering=1`。开机 S25 的 `/etc/init.d/packet_steering` 会给
**每个设备挑一个「最空闲核」写单核 rps_cpus**；而且它在 network / firewall reload 与
`interface.*` 事件后**自动重跑** —— 手工写的掩码会被覆盖。

**解决**：`scripts/45-set-rps-masks.py` 三层防线：`/usr/bin/rps-tuning.sh`
（eth0/wan/lan = `7` 三核、Wi-Fi vif = `6` 两核）+ `/etc/rc.local` 开机调用 +
`packet_steering` 的 `reload_service` 末尾挂钩子。

**验证**：`/etc/init.d/packet_steering reload` 后掩码仍为 7/6（不会被覆盖）；
满速下载时 `/proc/net/softnet_stat` 各核 dropped 为 0。

**教训**：凡是 OpenWrt 动态服务会改写的内核参数，都要「部署脚本 + 开机调用 + 钩在改写者之后」三件套。
完整原理见 `docs/06-CPU与收包性能调优.md`。

## 坑 19：DNS 去广告上线后「DNS 像是全挂了」，以及更新被自己的守卫跳过

**现象**：把广告清单挂上 dnsmasq 后立刻 `nslookup`，**清单内域名和正常域名一起超时**，
看着像 dnsmasq 挂了；同时 overlay 可用空间掉到 1.3MB，而脚本里设的「空间下限」会让
后续每次更新都直接被跳过。

**定位**：

```sh
ps w | grep '[d]nsmasq'                 # 会看到两个进程：ujail 外壳 + 真正干活的
logread | grep -i dnsmasq | tail -8     # 关键一行：read /etc/dns-blocklist.hosts - 109446 names
df -k /overlay                          # 可用空间；隔几分钟再采一次，看有没有变化
```

**根因**（三条叠加，都不是「坏了」）：

1. `reload` 后 dnsmasq 要**重新读入整张表**。10.9 万条在这颗 880MHz CPU 上要 **5~10 秒**，
   这期间查询必然超时 —— **不是服务挂了，是还没读完**。
2. `pgrep -x dnsmasq` 会匹配到 **ujail 外壳进程**（它的 comm 也叫 dnsmasq），
   该进程 VmRSS 只有 1MB 左右，看着像「清单没被加载」。真正干活的是 `/usr/sbin/dnsmasq`。
3. **jffs2 不会主动回收脏块**：反复改写 2.9MB 的清单文件，未回收的脏块会让可用空间
   长期偏低（实测 4 分钟不变）。如果「更新前的空间下限」设得比这个瞬时值还高，就会形成
   **「空间不足 → 跳过更新 → 空间永远不回收」的死锁**。

**解决**：见 `scripts/46-setup-dns-adblock.sh` 与 `docs/07-DNS去广告.md`：

- 验证前先**轮询等 dnsmasq 就绪**（查到正常域名能解析为止），再判定成败；
- 看内存只认 `/usr/sbin/dnsmasq`；
- 空间下限只盖住「新清单压缩后的大小」（800KB），真正的兜底是**写失败即中止、保留旧清单**；
- 默认把清单裁到 6 万条，并**用等间隔抽样而不是 `head`**（清单是按字母序排的，
  `head` 会把 m~z 段整段丢光）。

**验证**：`nslookup doubleclick.net 127.0.0.1` 返回 `Address: 0.0.0.0`；
对照域名返回真实 IP；`logread` 里读到的条数应等于 `wc -l /etc/dns-blocklist.hosts`。

**教训**：**「服务不可用」要先排除「正在忙」**——大文件重载期间的表现与崩溃几乎无法区分，
所以验证脚本必须自带等待。另外，给系统设「自保护阈值」时，阈值要用**实测的瞬时值**做下界，
否则保护本身会变成新的故障源。

## 坑 20：酷安 App 图片/图标加载不出（`custom_ua` 的 11 字节截断 + EdgeOne WAF 白名单）

**现象**：手机连 K2P WiFi 刷酷安，图片和图标全部加载不出，但网页浏览、文字内容都正常；
手机切流量（4G）立刻正常。

**定位**：

```sh
# 1. 全局停用 UA2F 后图片恢复 -> 根因在 UA2F，但 nfqueue_workers 1->4 无效
/etc/init.d/ua2f stop

# 2. 服务器侧抓到非标拦截：image.coolapk.com 明文 80 返回 HTTP 567 + 7KB HTML
#    响应头 Server: TencentEdgeOne、EO-LOG-UUID —— 腾讯 EdgeOne 的 WAF 拦截页
#    HTTPS 443 同样 567（443 不经 UA2F，说明拦的是"请求特征"不是"被改坏的包"）

# 3. UA 矩阵（443 绕开 UA2F 自由指定 UA，二分出 WAF 白名单）
#    裸 Mozilla / Mozilla/5.0 / Mozilla/5.0 (Linux...) Chrome/... -> 567
#    UA 里含 "safari"（不分大小写，连斜杠都不用，"Safari" 6 字节即可）-> 200
#    UA 含 MicroMessenger -> 200；Firefox / Dalvik / curl / python -> 567

# 4. 决定性的一手：回显服务看 UA2F 线上真实改写值（明文 80 经 UA2F，须在客户端发起）
curl -s http://httpbin.org/get | grep User-Agent
# uci 里写的 custom_ua 是 PROBE_UA_12345，线上收到的却是 PROBE_UA_12 —— 截断了！
```

**根因**（三层叠加，每层都单独排查过）：

1. **UA2F 的 `custom_ua` 有 11 字节硬截断**。二进制里就写着
   `Config user agent string is too long, truncating to %zu bytes`，实测写入
   `PROBE_UA_12345` 只生效 `PROBE_UA_12`。于是之前设的「完整浏览器 UA」
   实际生效的只是 `Mozilla/5.0 ` —— **配置文件里的值从来不是真实值**。
2. **腾讯 EdgeOne 对 `image.coolapk.com` 开了 UA 白名单 WAF**，认的是
   `safari` / `MicroMessenger` 这类**关键字**（不区分大小写、不要求完整指纹），
   `Mozilla/5.0` 这种残缺 UA 直接拦成 567。酷安图片恰好走明文 HTTP 80 且域名挂在 EdgeOne，
   才精准踩中；`avatar.coolapk.com` 没这条规则，所以头像正常、图片挂。
3. 附带发现该 WAF 还拦 **`Accept: image/*` 开头的请求**（任何 UA、任何出口都拦，
   4G 也拦）——但酷安 App 自己的图片请求不带这个头，属于酷安服务端的配置问题，与路由器无关。

**解决**：`custom_ua` 改成 **11 字节内且含 `Safari/` 关键字**的值：

```sh
uci set ua2f.main.custom_ua='Safari/537.'   # 11 字节，正好顶着截断上限
uci commit ua2f
/etc/init.d/ua2f restart
```

**验证**（以下命令全部在**内网客户端**执行，不是在路由器上）：

```sh
# 1. 回显确认线上真实改写值
curl -s http://httpbin.org/get | grep User-Agent      # "User-Agent": "Safari/537."

# 2. 酷安图片全链路（明文 80 经 UA2F 改写 -> WAF -> 图片字节）
curl -s -o t.bin -w '%{http_code}' -H 'Accept: */*' \
  'http://image.coolapk.com/image/...png'             # 200
head -c 4 t.bin | hexdump -C | head -1                # 89 50 4e 47 (PNG 文件头)
```

> **执行位置不能错**：UA2F 只处理 `iifname br-lan` 的转发流量，路由器自己发出的包不进
> NFQUEUE。在路由器上跑同一个回显，看到的是 `uclient-fetch` 自己的 UA —— 会把「已生效」
> 误判成「没生效」（2026-10-22 实测对照，见 04 篇 2.2）。

**教训**：

1. **「改了配置没生效」先怀疑截断/解析，用回显服务看线上真实值**——别信配置文件里的值。
   `curl http://httpbin.org/get`（明文 80，**从内网客户端发起**）是零成本的 UA 回显手段；
   在路由器上发起则无效（流量不进 NFQUEUE）。
2. **WAF 的 UA 白名单认的是关键字不是「像不像真浏览器」**：写得再像 Firefox 也没用，
   带上 `safari` 一词就能过。伪装 UA 的正确姿势是**覆盖关键字**，不是堆完整指纹。
3. **A/B 排查要全局开关**：之前只按域名旁路部分 IP 的做法因 DNS 轮换漏包而误判，
   全局 `stop`/`start` 才拿到干净结论。
4. **测试工具自身的 UA 会污染结论**：curl/python 的 UA 本来就被 WAF 拦，
   用它们测「某 UA 是否被拦」时，必须显式 `-H 'User-Agent: ...'`。
5. 顺带厘清：**校园网认证与 `custom_ua` 完全无关**——ESurfingClient 走加密协议，
   认证/心跳固定用 `CCTP/WinSVR5/1068`（按 `channel` 配置生成），不看明文流量的 UA。

## 坑 21：IT之家 App 打不开（校园网出口阻断 CDN 节点 443，ICMP 却通）

**现象**：手机连 K2P WiFi 打开 IT之家 App 一直转圈 / 加载失败；切 4G 立刻正常。
首页、其他网站、其他 App 全部正常，只有 IT之家不行。

**定位**：

```sh
# 1. App 侧 logcat 直接给出目标与超时
#    SocketTimeoutException: failed to connect to napi.ithome.com/175.12.90.41
#    (port 443) after 10000ms
adb -s <serial> logcat | grep -iE 'ithome|SocketTimeout'

# 2. 手机 conntrack：到 175.12.90.41:443 全是 SYN_SENT [UNREPLIED]
#    —— SYN 发出去没有任何回应，不是应用层错误

# 3. 分层验证（PC 同出口）
ping 175.12.90.41                 # 通，17ms，0% 丢包
curl -m 10 https://napi.ithome.com/   # 超时（000）
curl -v --max-time 5 telnet://175.12.90.41:443   # TCP 连不上（跨平台写法）
# Windows PowerShell 等价：Test-NetConnection 175.12.90.41 -Port 443 → TcpTestSucceeded: False
curl -m 10 https://api.ithome.com/    # 200（同站其他域名正常）

# 4. 换 DNS 全部无效：阿里 / 腾讯 / 114 / Google / 运营商 / DoH
#    一律返回 175.12.90.41 —— 解析是对的，问题在"到该 IP 的路径"

# 5. 决定性对照：手机切 4G（电信），测同一个 IP
#    napi 解析仍是 175.12.90.41，访问却返回 404 / 0.21s
#    —— 同一节点、同一时刻，换出口就通
```

**根因**：校园网出口线路对部分 CDN 节点 IP 做了端口级过滤/QoS（大流量 CDN 常被归类限速或阻断），
**ICMP 放行、TCP 443 丢弃**。CDN 按出口调度把校园网分配到了这个节点，
而 4G 电信出口到同一节点却是通的。所以既不是节点故障，也不是 DNS 解析错误。

**解决**：用 dnsmasq 域名覆盖，把该域名固定到实测可达的节点（绕开被阻断的那个 IP）：

```sh
uci add dhcp domain
uci set dhcp.@domain[-1].name='napi.ithome.com'
uci set dhcp.@domain[-1].ip='183.131.62.41'
uci commit dhcp
/etc/init.d/dnsmasq restart
```

备用节点（均实测从校园网出口可达，任选其一替换上面的 IP）：

| 地区 | IP | 响应 |
|---|---|---|
| 江苏（默认） | 183.131.62.41 | 0.18s |
| 北京 | 123.244.92.41 | 0.26s |
| 上海 | 218.94.231.41 | 0.18s |
| 浙江 | 122.228.115.41 | 0.20s |
| 四川 | 182.242.223.99 | 0.18s |

**验证**：

```sh
nslookup napi.ithome.com 127.0.0.1          # Address: 183.131.62.41（覆盖生效）
curl -s -o /dev/null -w '%{http_code} %{time_total}s' https://napi.ithome.com/   # 404 0.23s
# 手机侧：404 / 0.20s，App logcat 不再出现连接错误
```

**教训**：

1. **ping 通 ≠ 服务可达**。`ICMP 通 + TCP 断`是"路径策略/端口过滤"的典型指纹，
   排查必须落到 TCP 层（`curl -w '%{time_total}'` 或 `Test-NetConnection -Port`）。
2. **CDN 类问题必须做「第二出口」对照**。只有 4G 同节点可通，才能把结论从
   「节点坏了」纠正为「校园网出口阻断」——否则修复方向会完全错（等 CDN 修复 vs 换节点）。
3. **换公共 DNS 解决不了「解析正确但节点不可达」**：所有 DNS 都返回同一 IP，
   换 DNS 只会改变解析延迟，不会改变路径。
4. **DNS 覆盖是最轻量的绕行手段**，但要先备好可用节点清单，节点失效时一分钟就能换。

## 坑 22：改 DNS 上游把全屋解析搞挂（CNNIC 超时 + 校园 DNS 只给 IPv6 + 撤覆盖叠加）

**现象**：为解决坑 21，尝试「撤掉电信 DNS 换 CNNIC」并撤掉域名覆盖后，
napi 再次打不开，紧接着 `www.baidu.com` 也解析失败（No answer）——故障从单个 App 扩大到全屋 DNS。

**定位**：

```sh
nslookup napi.ithome.com 127.0.0.1        # ;; connection timed out（dnsmasq 解析不了）
nslookup napi.ithome.com 1.2.4.8          # 从路由器查 CNNIC 超时（从 PC 查却是 32ms）
nslookup napi.ithome.com 172.16.2.17      # 超时
nslookup napi.ithome.com 172.16.2.1       # 只返回 IPv6 AAAA（设备无公网 IPv6，用不上）
nslookup www.baidu.com 127.0.0.1          # Can't find www.baidu.com: No answer
```

**根因**（三件事叠加）：

1. **CNNIC 从路由器发起查询会超时**（PC 经 NAT 查正常 32ms，路由器本机查被丢）——
   「DNS 可用」的判断必须从实际发起方测。
2. **校园 DNS 两个地址都不可靠**：172.16.2.17 超时，172.16.2.1 只给 AAAA 记录，
   而 LAN IPv6 已关闭（见坑 14），拿到 IPv6 地址也无法访问。
3. **域名覆盖是当时唯一稳定的解析来源**。撤掉覆盖后，napi 完全依赖上述失效上游，
   同时 dnsmasq 对普通域名的解析也被拖垮。

**解决**：回滚到稳定组合（加回电信 DNS + 恢复域名覆盖），验证恢复：

```sh
uci add_list dhcp.@dnsmasq[0].server='202.96.128.86'
uci add dhcp domain
uci set dhcp.@domain[-1].name='napi.ithome.com'
uci set dhcp.@domain[-1].ip='183.131.62.41'
uci commit dhcp
/etc/init.d/dnsmasq restart
```

回滚后：`www.baidu.com` 正常解析、napi 返回覆盖 IP、PC 访问 404/0.24s、网络 ping 正常。

**教训**：

1. **一次只改一个变量**。同时「换上游 DNS」和「撤覆盖」导致两个故障源叠加，定位成本翻倍。
2. **DNS 可用性要从实际发起方验证**。路由器本机与内网 PC 的出口/策略可能不同
   （本例 CNNIC 对路由器超时、对 PC 正常）。
3. **覆盖规则是兜底，撤它之前先确认上游能返回可用节点**——否则等于拆掉唯一的桥。
4. **校园 DNS 不适合做唯一上游**：一个地址超时、另一个只给 AAAA；
   且冷解析实测 237ms（转发 + 审计），电信 DNS 仅 12ms，差 20 倍。
   校园 DNS 只适合处理校内域名（按域名转发）。

## 排错通用心法

1. **先分层定位**：认证问题看 `logread | grep esurfing`；无线问题看 `iw`；转发问题看 `nft list ruleset`。
2. **验证要可证伪**：不要「看起来好了」，要构造反证。比如验证 TTL 归一化，就临时把 LAN 出向 TTL 改成别的值，看 WAN 出口是否仍是 64。
3. **重启即失忆（默认），本方案已做持久化**：`/var/log` 在 tmpfs，重启即清空；
   本项目已把日志落到 `/etc/log/messages` 并记录启动历史（见 `08-持久日志与重启诊断.md`）。
   但断电瞬间最后几秒仍可能来不及落盘，关键取证先导出。
4. **改配置必落盘**：运行时的 nft/uci 修改一定要 `uci commit` 或写进开机脚本。
5. **一次只改一个变量**：同时改多个配置，出问题无法定位。
