# 01 · 运营商是怎么检测多设备的

要对抗检测，先要理解检测。校园网的多设备检测大致分三类：**认证层**、**应用层指纹**、**网络层指纹**。

---

## 一、认证层：一人一号 / 一设备一号

最常见的形态是基于 MAC 或 Portal 会话的认证：

- **802.1X / Portal 认证**：运营商在接入侧（BRAS / AC）维护一个「账号 ↔ 在线设备」表。同一账号第二次认证时，要么拒绝，要么顶掉前一台。
- **一设备一号**：更狠，直接把账号和某个设备指纹绑定。检测手段通常就是下面第二、三类。

**破解思路**：让**路由器**成为唯一完成认证的设备。路由器后面挂多少台设备，对运营商来说都是 NAT 后的一台设备。

> 关键点：路由器本身要能完成认证。天翼校园网用的是 `ESurfingClient`，其它学校可能是 `Dr.Com`、`Srun`（深澜）、`锐捷` 等，原理类似，替换认证客户端即可。

---

## 二、应用层指纹：User-Agent

这是**最容易被忽略、也最容易泄露**的一层。

同一局域网里的设备，HTTP 请求的 `User-Agent` 各不相同：

```
Windows 笔记本 : Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ... Chrome/131 ...
iPhone         : Mozilla/5.0 (iPhone; CPU iPhone OS 17_0 like Mac OS X) ... Version/17.0 Mobile/15E148 ...
Android 手机   : Dalvik/2.1.0 (Linux; U; Android 13; ...)
智能音箱        : okhttp/3.12.0
```

只要出口流量里同时出现 `Windows`、`iPhone`、`Android` 等多种 UA，检测设备立刻就能判断「这个 IP 后面不止一台设备」。

**破解思路**：把内网所有 HTTP 请求的 UA **统一改写成同一个字符串**。

### 为什么选 UA2F 而不是 Privoxy / xmurp-ua

| 方案 | 原理 | 缺点 |
|---|---|---|
| Privoxy | 代理转发 80 端口流量 | 只能处理 80 端口；非标端口的 HTTP（如手机 QQ 图片走 8080）漏掉 |
| xmurp-ua | 内核模块挂 netfilter | 内核模块崩溃会连累整个内核，可能随机挂起 |
| **UA2F** | 用户态程序 + NFQUEUE | 性能有开销（可接受），但崩了不影响内核 |

UA2F 的工作方式：

1. 防火墙把包交给 `NFQUEUE`；
2. UA2F 在用户态判断「TCP 首个报文是否以 `GET`/`POST` 等 HTTP method 开头」；
3. 是 HTTP 就解析头部，找到 `User-Agent` 并**等长替换**；
4. 替换后的包放回队列继续正常转发。

因为**替换前后长度一致**，TCP 序号、服务端 ACK 都不需要额外追踪，实现简单且稳定。

> 参考：UA2F 作者 Zxilly 的原始说明 —— <https://github.com/Zxilly/UA2F>
> 相关实践文章 —— <https://learningman.top/archives/304>

### 等长替换带来的一个坑

等长替换意味着 **`custom_ua` 的实际写入长度取决于原始 UA 的长度**：

- 原始 UA 比 `custom_ua` 长 → 截取 `custom_ua` 的前 N 个字符（正常）
- 原始 UA 比 `custom_ua` 短 → 只替换前 N 个字符，**剩下的是原始 UA 的残串**

举例（`custom_ua = Mozilla`，7 字节）：

| 原始 UA | 长度 | 改写结果 | 说明 |
|---|---|---|---|
| `Mozilla/5.0 (Windows NT 10.0 ...)` | 110 | `Mozilla` | ✅ 完美 |
| `Dalvik/2.1.0 (Linux; U; Android 13)` | 35 | `Mozilla` | ✅ 完美 |
| `okhttp/3.12.0` | 13 | `Mozilla` | ✅ 完美 |
| `curl/8.5.0` | 10 | `Mozilla/5.` | ⚠️ 残留 `/.` |
| `okhttp` | 6 | `Mozill` | ⚠️ 残串 |

**结论**：`custom_ua` 越短，覆盖范围越广。用 `Mozilla`(7B) 时，只有原始 UA 短于 7 字节才会残留，而现实中几乎没有这么短的 UA。这就是为什么本方案最终把 `custom_ua` 定成了 `Mozilla`。

## 三、网络层指纹：TTL / HopLimit

每台设备发出的 IP 包都有一个 TTL（IPv6 是 HopLimit），由操作系统决定：

| 操作系统 | 默认 TTL |
|---|---|
| Windows | 128 |
| Linux / Android | 64 |
| macOS / iOS | 64 |
| 部分路由器 / 网络设备 | 255 |

检测设备只要看出口流量的 TTL 分布，就能判断后面有几类系统。

**破解思路**：在 WAN 出口把所有包的 TTL 统一设为 64。

```
table inet ttl_normalize {
    chain postrouting {
        type filter hook postrouting priority mangle + 10; policy accept;
        oifname "wan" ip ttl set 64
        oifname "wan" ip6 hoplimit set 64
    }
}
```

> 选 64 是因为 Linux 系（含 OpenWrt 本身、Android）默认就是 64，改完之后「路由器自己」和「后面的设备」看起来完全一致。

## 四、时间层指纹：NTP / 时钟偏差

有些检测方案会看 NTP 行为或时钟特征：

- 多台设备各自向外部 NTP 服务器发起请求 → 出口出现多个 NTP 会话，暴露设备数量；
- 各设备时钟存在微妙偏差 → 可被用于设备区分。

**破解思路**：让路由器做内网唯一的 NTP 服务器，把内网所有 NTP 请求劫持到路由器本地。

```
table inet ntp_redirect {
    chain prerouting {
        type nat hook prerouting priority dstnat; policy accept;
        iifname "br-lan" ip daddr != 192.168.1.0/24 udp dport 123 counter redirect to :123
    }
}
```

配合路由器开启 NTP 服务端模式（`system.ntp.enable_server='1'`），内网设备无论配置的是哪个 NTP 服务器，最终都会从路由器拿时间。

> 注意：这条规则只作用于 `iifname "br-lan"`（内网入向），路由器自己的上游 NTP 同步走的是 `output` 链，不受影响。

---

## 五、还有哪些特征值得关注

UA2F 作者的原始文章里还提到过 DNS 劫持、深信服设备等场景。本方案目前覆盖了 UA / TTL / NTP 三类。如果学校用的是更激进的检测（如统计学流量特征、TCP 指纹、时钟精确分析），可能需要进一步的手段（例如 DNS 强制重定向、TCP 栈参数归一化等）。

**排查原则**：先用抓包确认学校到底在检测什么，再对症下药，不要盲目堆规则。
