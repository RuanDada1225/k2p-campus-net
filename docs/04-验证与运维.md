# 04 · 验证与运维

配置写完不代表生效。这一篇给出**可证伪**的验证方法，以及日常运维要点。

---

## 一、一键体检脚本

把下面这段存成 `/tmp/health.sh` 丢到路由器执行，可以快速看清全局状态：

```sh
#!/bin/sh
echo "=== 系统 ==="
uptime; free

echo "=== 服务 ==="
for s in ua2f esurfingclient sysntpd uhttpd dnsmasq; do
    ubus call service list "{\"name\":\"$s\"}" 2>/dev/null | grep -q '"running": *true' \
        && echo "$s: running" || echo "$s: STOPPED"
done

echo "=== nft 表 ==="
nft list tables

echo "=== WAN ==="
ip -4 addr show wan | grep inet
ip route | grep default
ping -c 2 -W 2 223.5.5.5 | tail -2

echo "=== UA2F ==="
ps w | grep -E '[u]a2f'
logread | grep -icE 'conntrack catch error' | sed 's/^/conntrack errors: /'

echo "=== 认证 ==="
logread | grep -i esurfing | tail -4

echo "=== 无线 ==="
iw dev 2>/dev/null | grep -E 'Interface|channel|txpower'

echo "=== 空间 ==="
df -h /overlay | tail -1
```

## 二、逐层验证方法

### 2.1 认证层

```sh
logread | grep -i esurfing | tail -20
```

**通过标准**：看到认证成功 + 周期性「发送心跳包」；无「提取门户配置失败」「等待网络服务超时」。

```sh
ip -4 addr show wan          # WAN 有运营商分配的地址
ip route | grep default      # 有默认路由
ping -c 3 223.5.5.5          # 外网可达
```

### 2.2 应用层（UA2F）

从**内网设备**访问 <http://ua-check.stagoh.com/>，查看回显的 UA 是否已被统一为 `Mozilla`。

批量验证不同长度的 UA（用 `scripts/90-verify-ua-length.py`）：

```
orig_len=110  ->  result_len=7  result='Mozilla'      ✅
orig_len= 35  ->  result_len=7  result='Mozilla'      ✅
orig_len= 13  ->  result_len=7  result='Mozilla'      ✅
orig_len= 10  ->  result_len=7  result='Mozilla/5.'   ⚠️ 残留
orig_len=  6  ->  result_len=6  result='Mozill'       ⚠️ 残串
```

**通过标准**：现实中常见的 UA（≥7 字符）全部被改成 `Mozilla`。

确认 nft 规则只处理 br-lan：

```sh
nft list table inet ua2f | grep queue
# meta l4proto tcp ct direction original iifname "br-lan" counter ... queue ... to 10010
```

### 2.3 网络层（TTL）

**反证法**：临时把 LAN 出向 TTL 改成 55，在 WAN 侧抓包，若仍是 64 则说明归一化生效。

```sh
# 加载反证表
nft -f - <<'EOF'
table inet ttl_probe {
    chain postrouting {
        type filter hook postrouting priority mangle + 20; policy accept;
        oifname "br-lan" ip ttl set 55
    }
}
EOF

# 在内网设备 ping 外网，同时在路由器 WAN 侧抓包
tcpdump -ni wan -c 5 'icmp' -v
# 观察 TTL 字段应为 64

# 删除反证表
nft delete table inet ttl_probe
```

### 2.4 时间层（NTP 重定向）

```sh
# 1. 确认路由器监听 123
netstat -lnup | grep ':123 '

# 2. 确认规则计数器增长
nft list table inet ntp_redirect

# 3. 内网设备向不可路由地址发 NTP 请求，收到合法应答即证明被劫持
#    （如 ntpdate -q 203.0.113.1）
```

## 三、重启持久性验证

**这是最重要的一环**。所有配置改完后必须重启一次，逐项确认：

```sh
# 重启前先把关键状态存下来
nft list ruleset > /tmp/before_reboot.txt
sysctl -a 2>/dev/null | grep rmem > /tmp/before_reboot_sysctl.txt

reboot
```

重启后（等约 1 分钟）逐项核对：

| 检查项 | 命令 | 期望 |
|---|---|---|
| UA2F 运行 | `pgrep -af ua2f` | 有进程 |
| UA2F 只处理 br-lan | `nft list table inet ua2f \| grep queue` | 含 `iifname "br-lan"` |
| TTL 归一化 | `nft list table inet ttl_normalize` | 表存在 |
| NTP 重定向 | `nft list table inet ntp_redirect` | 表存在 |
| rmem | `sysctl net.core.rmem_max` | `4194304` |
| 时区 | `date` | 北京时间 |
| 认证 | `logread \| grep esurfing` | 一次认证成功，无退避 |
| 5G 信道 | `iw dev phy1-ap0 info \| grep channel` | 149 |

**若某项丢失**，说明它没有落到 overlay 里的开机脚本 —— 回到对应章节补上持久化。

## 四、日常运维

### 4.1 日志

```sh
logread | tail -50                      # 最近日志
logread | grep -iE 'error|fail' | tail  # 只看错误
```

> **重要**：`/var/log` 在 tmpfs（内存），**重启即清空**。需要留存的历史日志必须在重启前导出到 overlay：
> ```sh
> logread > /overlay/root/last-boot.log
> ```

### 4.2 空间管理

```sh
df -h /overlay
du -sh /overlay/upper/* 2>/dev/null | sort -h | tail
```

overlay 只有 7.6MB，装插件前务必先看空间。可清理的：`/tmp/*`（内存，重启自动清）、`/overlay/root/*.log`。

### 4.3 认证稳定性监控

```sh
# 看心跳是否规律（天翼 250s 一次）
logread | grep -i esurfing | grep 心跳 | tail -10
```

若心跳间隔异常或频繁重认证，可能是校园网侧策略变化，需要重新抓包分析。

### 4.4 断网自愈（watchcat）

已配置 watchcat：探测 `223.5.5.5`，6 小时（21600s）无响应则重启。

```sh
uci show watchcat
pgrep -af watchcat.sh
```

### 4.5 流量统计（nlbwmon）

```sh
uci show nlbwmon
# 默认数据库在 tmpfs，重启清空（本项目未做持久化以节省 overlay）
```

## 五、安全基线

配置完成后，确认以下几点（默认 OpenWrt 通常已满足）：

| 项 | 命令 | 期望 |
|---|---|---|
| WAN 入向拒绝 | `uci show firewall.@zone[1]` | `input='REJECT'` `forward='DROP'` |
| 端口转发 | `uci show firewall \| grep redirect` | 未配转发时为空；若配了（见 05 篇）应只有预期的那几条 |
| DNS 仅本地服务 | `uci show dhcp.@dnsmasq[0].localservice` | `1` |
| DNS 反重绑定 | `uci show dhcp.@dnsmasq[0].rebind_protection` | 默认 `1`；若为 `0`（见 03 篇坑 13），确认是有意为之 |
| SSH 密码强度 | —— | 别用弱密码（本文示例已脱敏） |

> 配了端口转发后，WAN 上就多了几个入口。请对照 `docs/05-固定IP与远程访问.md`
> 的安全章节逐条确认：端口是否必要、目标是否固定、口令是否够强。

## 六、已知限制

- **无线功率**：K2P 的 MT7615 被驱动硬限制在 8 dBm，配置层无解。
- **加密流量**：UA2F 无法改写 HTTPS（TLS 加密），只能处理明文 HTTP。
- **UA 极短残串**：原始 UA 短于 `custom_ua` 长度时会残留，但现实中罕见。
- **无硬件 RTC**：K2P 没有 RTC，冷启动瞬间时间不准，NTP 同步前可能有短暂偏差。
- **DFS 信道**：5G 若用 DFS 信道会有 CAC 延迟，建议固定非 DFS 信道。
